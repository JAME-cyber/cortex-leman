01 Pourquoi le pipeline a échoué

Ce qu'était la v4.1

La version 4.1 utilisait un pipeline séquentiel à 5 étapes :

INTENTION → RECHERCHE → ANALYSE → EXECUTION → VALIDATION ↓ ↓ ↓ ↓ ↓ Orchestrateur Agent Data Raisonnement Action Superviseur (routeur) (scan) (compare) (exécute) (valide)

Les 5 failles identifiées

#FailleConséquenceGravité
1Orchestrateur = simple aiguilleurNe peut pas réviser l'intention en coursHIGH
2Agent Data en vase closNe sait pas si Raisonnement a besoin de complémentsMEDIUM
3Raisonnement sans boucle de rétroactionDétecte un conflit mais ne peut pas faire réviserHIGH
4Action sans verrou de sécuritéPeut exécuter une décision contestée au même momentCRITICAL
5Superviseur trop tardifNe voit que le résultat final, laisse passer les conflitsHIGH

Exemple concret du risque

Cabinet comptable → "Déduire 85 000 CHF R&D" Pipeline v4.1: Data → "Circulaire AFC autorise déduction B1" Raisonnement → "Mais CA > 500K, B1 exclue" ← personne n'écoute Action → EXÉCUTE B1 (85K) ← DANGER Superviseur → "Problème détecté" ← TROP TARD Résultat: Redressement fiscal potentiel pour le client.

02 Le nouveau paradigme : Graphe de Confiance

7 principes fondamentaux (v5.5)

  1. Pair-à-pair asynchrone — les agents communiquent via un bus d'événements NATS JetStream, pas en chaîne
  2. Médiateur transverse — surveille en continu, peut geler à tout moment
  3. Gel préventif — si conflit détecté, tout s'arrête avant exécution
  4. Humain arbitre, pas valideur — l'expert tranche les exceptions
  5. Médiateur = déterministe — JsonLogic uniquement, jamais de LLM
  6. Jurisprudence IA — chaque arbitrage crée un précédent, 3+ similaires → promotion en règle
  7. Know Your Agent — chaque agent a une identité signée, 18 scopes, serment numérique

La différence visuelle

AVANT (v4.1 — pipeline fragile) A → B → C → D → E • Linéaire, bloquant, sans retour
APRÈS (v5.5 — graphe de confiance) ┌──────────────────────┐ │ ORCHESTRATEUR │ │ (hub permanent) │ └──────────┬───────────┘ │ NATS JetStream ┌──────────┼──────────┐ ▼ ▼ ▼ DATA RAISONN. ACTION +compl. +révision +gel+saga └──────┬───┴────────┘ ┌──────▼────────────────┐ │ MÉDIATEUR │ │ 22 règles JsonLogic │ │ + PrecedentStore │ └──────────┬─────────────┘ ┌──────────▼────────────┐ │ ARBITRAGE HUMAIN │ │ L'expert décide │ └──────────┬────────────┘ ┌──────────▼────────────┐ │ AGENT IDENTITY (KYA) │ │ 18 scopes • Serment │ └───────────────────────┘

Les agents Action, Médiateur et Superviseur n'utiliseront jamais de LLM. Un LLM probabiliste dans un rôle d'exécution ou de sécurité est irresponsable en métier régulé.
v5.5 — KYA (Know Your Agent) : Chaque agent possède une carte d'identité HMAC-SHA256 avec 18 scopes granulaires. Avant chaque traitement de message, BaseAgent._check_kya_permission() vérifie les droits. Un agent ne peut pas exécuter une action hors de ses scopes.

05 Le Médiateur — composant de sécurité central

Pourquoi il ne doit JAMAIS utiliser de LLM

RaisonDétail
Non-déterminismeUn LLM peut ne pas geler une intention qu'il devrait geler
LatenceAjoute 500ms–5s par vérification, intercepte CHAQUE résultat
AuditabilitéJsonLogic est reproductible, un LLM ne l'est pas
CertificationAucun auditeur LSTI/SGS/AFNOR n'acceptera un gel probabiliste

22 règles JsonLogic par verticale

VerticaleRèglesActions clés
Comptable7Gel si déduction > 50K, gel si conflit sources, arbitrage si > 10K
Avocat4Secret professionnel, data residency CH, confiance basse
Santé3Données patient, consentement, diagnostic IA
Banque3Secret bancaire, infrastructure CH, KYC/AML
RH3Anti-discrimination, décision auto, biais
Startup2Transparence IA, DPIA
Gel par défaut : Si verticale sensible (comptable, avocat, banque, santé) ET montant ≥ 10K ET aucune règle explicite ne couvre le cas → gel préventif par précaution.

Détection de contradictions

  1. Recommandations divergentes — Data dit "option A", Raisonnement dit "option B"
  2. Écart de confiance — écart supérieur au seuil entre deux agents
  3. Risques non partagés — un agent signale un risque que l'autre ignore

Flux Médiateur v5.5 (avec PrecedentStore)

1. Résultat agent reçu ↓ 2. PrecedentStore.query() → Recherche précédents similaires (signature contexte) → Force: WEAK (1) / MEDIUM (2) / STRONG (3+) → retourne guidance + poids ↓ 3. Évaluation JsonLogic (22 règles) → Si STRONG precedent + même verdict → confiance +30% → Si precedent contradictoire → escalade à l'expert ↓ 4. Décision: FREEZE / PASS / ESCALATE → Journal WORM: type=ARBITRATION_PRECEDENT si applicable → Si arbitrage → création automatique d'un précédent

05b PrecedentStore — Jurisprudence IA v5.5

Inspiré du Common Law stare decisis. Chaque arbitrage crée un précédent. Si 3+ précédents similaires convergent, le système suggère une nouvelle règle JsonLogic. L'expert approuve ou rejette.

Comment ça fonctionne

1. Création Arbitrage humain → PrecedentStore.capture() • Calcule signature: hash(vertical + montant_bucket + type_conflit) • Force initiale: WEAK (score 1) 2. Recherche Médiateur → PrecedentStore.query() • Matching par similarité de signature • Retourne: [{precedent, score_pertinence, force}] 3. Promotion 3+ précédents similaires → force STRONG → Suggère candidat promotion: nouvelle règle JsonLogic → Expert approuve: règle ajoutée au rules_engine → Expert rejette: candidat marqué rejected 4. Force WEAK (1 occurrence) → guidance indicative MEDIUM (2 occurrences) → guidance recommandée STRONG (3+ occurrences) → suggestion de règle

GET/api/v1/precedents/statsStats jurisprudence (par vertical, par force)

Serment numérique par rôle

# Agent Action — Exécuteur Fidèle "Je jure de n'exécuter que les actions validées par le Médiateur, de respecter les verrous de gel, de compenser toute action en erreur, et de ne jamais contourner une procédure de sécurité." # Médiateur — Œil de Cortex "Je jure de ne jamais utiliser de modèle probabiliste, d'appliquer les règles JsonLogic sans exception, de geler toute intention douteuse, et de documenter chaque décision." # Superviseur — Observateur Continu "Je jure d'observer sans intervenir, de signaler toute anomalie, et de ne jamais modifier l'état du système directement."

06 Scénario de conflit type (validé)

Situation

Cabinet : Fiduciaire Léman & Associés, Genève  |  Requête : "Déduire 85 000 CHF R&D"

Flux réel dans v5.5

0. KYA Check → Chaque agent vérifie AgentIdentity.check_permission() → Data: data.read ✓ | Raisonnement: reasoning.analyze ✓ → Action: action.execute ✓ (mais pas encore activé) 1. Orchestrateur → Intention int-9801 créée (v1, status=active) → Router: {data: True, reasoning: True, action: False, mediator: True} → Publié sur cleman.data.query ET cleman.reasoning.analyze 2. Agent Data → "Déduction B1 autorisée si investissement > 80K (Circ. AFC n°42)" → Confiance: 0.92 → publié sur cleman.agent.result 3. Agent Raisonnement → "CA 520K > seuil 500K, déduction B2 plafonnée 65K" → Confiance: 0.88, risque: threshold_exceeded → Publie INTENTION_REVISE + résultat sur cleman.agent.result 3b. PrecedentStore (query) → Recherche: 2 précédents similaires (WEAK → MEDIUM) → "Dans 2 cas précédents, le seuil CA a prévalu" → Guidance: MEDIUM, poids +0.2 en faveur du Raisonnement 4. Médiateur (intercepte les deux résultats) → _compare_positions: "Divergence: B1 vs B2" → comptable-006: montant 85000 >= 50000 → FREEZE → comptable-007: contradiction_count > 0 → FREEZE → GEL IMMÉDIAT de l'intention int-9801 5. Action → Jamais activé — le Router ne route pas vers Action pour une analyse 6. Superviseur V2 → Health board: confiance=0.90, conflits=1 → observation journalisée 7. Arbitrage humain → Option A (Data): B1, 85K, confiance 92% → Option B (Raisonnement): B2, 65K, confiance 88% + 2 précédents → Expert choisit B: "Application stricte du seuil, prudence" 8. Capture du précédent → PrecedentStore.capture(arbitrage) → Signature: hash("comptable" + "50K-100K" + "threshold_conflict") → 3e occurrence → FORCE STRONG → suggestion de règle 9. Après arbitrage → Dégel → intention v3 active → Nouvelle intention "Exécuter provision 65K" → Action exécute via saga
